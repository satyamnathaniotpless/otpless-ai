## Notes

- `recruit-watch-applicant` at 5-minute polling is the compiled approximation of F9's "within minutes, any hour" — see `platform/contracts/notion.md` capability-gap note: there is no push/subscribe, only polling.
- Cron cadence choices (`*/5`, hourly, daily 08:30) are this integrator's proposal to satisfy PRD timing language; not sourced from a PRD-specified cron expression — confirm with the accountable human if a tighter/looser interval is wanted before this compiles into qm's live schedule.
- **Ordering dependency:** `recruit-evidence-rollup` (21:00 IST Sun) must run before `recruit-retro` (22:00 IST Sun) — the retro reads the rollup's bucket counts to decide which action-class to examine. The two open different PRs and must not be merged into one job: `recruit-evidence-rollup` opens **promotion** PRs against `command-policy.md` when a gate clears (`packs/shared/metrics/SKILL.md`), while `recruit-retro` opens **playbook/template** PRs against the agent's own config (`packs/shared/retro/SKILL.md`) — a human should never be asked to approve a tone change and an autonomy increase in one review. If the rollup is skipped or fails, no promotion PR is opened that week, and the retro still runs but must state that it had no fresh evidence.
- Any row whose action-class reaches L1 for that specific Slack send pattern (per `command-policy.md` §3, evidence-based, PR-merged) switches its output surface from "draft" to "auto-post" — this table's "output surface" column must be updated in the same PR that promotes the action-class.
- `onboard-watch-hire` at 15-minute polling is the compiled approximation of "offer-accepted → Onboarder takes over" (master PRD §4) — same capability gap as `recruit-watch-applicant`: no push/subscribe, only polling (`platform/contracts/notion-employees.md`).
- **Ordering dependency (onboarder):** `onboard-evidence-rollup` (21:00 IST Sun) must run before `onboard-retro` (22:00 IST Sun) — same rule as the `recruiter` scope above: the retro reads the rollup's bucket counts, the two open different PRs (promotion vs playbook/template) and must never be merged into one job or one human review. If the rollup is skipped or fails, no promotion PR is opened that week, and the retro still runs but must state it had no fresh evidence.
- **Ordering dependency (people-ops):** `people-ops-evidence-rollup` (21:00 IST Sun) must run before `people-ops-retro` (22:00 IST Sun), for the same reason and with the same failure behavior as above.
- `people-ops-payroll-cutoff-reminder`'s schedule is a placeholder pending the HRMS provider decision (gate G14, `docs/gates.md`) — the real cadence must match whichever vendor's actual payroll cutoff calendar is chosen; confirm and correct this row in the same change that closes G14, per `platform/contracts/hrms.md`.
- **Ordering dependency (analyst):** `analyst-evidence-rollup` (21:00 IST Sun) must run before `analyst-retro` (22:00 IST Sun), for the same reason and with the same failure behavior as the `recruiter` scope's ordering dependency above: the retro reads the rollup's bucket counts, the two open different PRs (promotion vs playbook/template) and must never be merged into one job or one human review.
- `culture-pulse-survey-cycle`'s schedule is a placeholder pending the pulse-survey tooling decision (gate G24, `docs/gates.md`) — the real cadence must match whichever tool is chosen (some tools batch quarterly, some monthly); confirm and correct this row in the same change that closes G24.
- **Ordering dependency (culture):** `culture-evidence-rollup` (21:00 IST Sun) must run before `culture-retro` (22:00 IST Sun), same rule and failure behavior as above — the retro reads the rollup's bucket counts, the two open different PRs and must never be merged into one job or one human review. This scope's retro also must never treat a review-cycle or exit-interview content edit as trust-ladder evidence — those classes are never-delegated (see `./scopes/culture.md`), not slow to promote.
