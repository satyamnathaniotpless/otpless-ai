# Native SDK Engineer — iOS

## Posting

- **Role:** Native SDK Engineer, iOS
- **Posting link:** OTPLESS careers page, role #3
- **Comp band:** ₹18–35L mid / ₹35–55L senior / ₹12–18L exceptional junior + ESOPs
- **Owner:** CTO

## Outreach hook patterns

- Reference a distributed library/package they shipped, not just an app: "saw your Swift package {name} — that's the SDK-engineering muscle this role needs."
- For App Store review veterans: mention navigating review edge cases as the hook.
- For app-only backgrounds with strong Swift fundamentals: soft pitch — "not sure if you'd be open to it, but this is a different sport from app dev."

## Candidate bar

**Hard requirements**
- Has shipped a distributed library/SDK, not only apps.
- Deep Swift (+ Objective-C interop); knows app lifecycle, keychain, entitlements cold.

**Strong signals**
- Cares about the integrating developer as much as the end user.
- Ships across SPM/CocoaPods/XCFramework without breaking anyone.
- Built own product / OSS contributor / identity-auth depth (universal preference, all roles).

**Auto-advance signals**
- Strong Q1 artifact — a real Swift package/SDK with adoption.
- Strong Q4 identity/auth/fraud depth answer.

**Auto-reject signals**
- App-only background, no SDK/library signal anywhere.
- Generic AI-written answers with no specifics about what they built.

## Work-sample brief

Design and partially implement a tiny event-logging SDK: define the public Swift API, versioning strategy, and a size budget; implement enough to demonstrate the API surface and one core logging call. 2–3 hours, AI tools required.

## Role-specific Q&A

| Question | Answer |
|---|---|
| Which distribution formats do you support? | SPM primary, CocoaPods and XCFramework maintained. |
| How do you handle privacy manifests / ATT? | You'll own that end-to-end — happy to go deep in the debrief. |

## Evaluation emphasis

API ergonomics and versioning/size discipline over feature completeness. Reward a small, boring, reliable public surface.
